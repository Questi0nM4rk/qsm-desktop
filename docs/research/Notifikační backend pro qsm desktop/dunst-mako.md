# Dunst and Mako as notification backends (research only)

As-of date: 2026-10-08. Scope: upstream Dunst and Mako only; not local code, other daemons, or runtime tests. “Headless backend” here means a daemon that owns notification protocol/state/actions/expiry while an external QML client owns all presentation.

## Decision summary

Neither upstream is a supported headless backend. Both are complete *notification daemons* that own a renderer/window stack as well as protocol state and timers. Mako is the closer integration candidate because it exposes list-current, history, actions, and change notification over a documented private D-Bus API. But it still requires Wayland, paints its own surfaces, and does not expose raw image data through its list API. Dunst is broader/more cross-platform and mature, but its private API exposes history rather than a current-notification snapshot, making robust external UI substantially harder. If qsm-desktop requires exact custom notifications, per-item hover pause, reliable QML restart recovery, and a single visible popup, implementing a Qt-side daemon/backend with its own store and policy is more honest than disguising either renderer as headless.

## Protocol and backend capability matrix

| Requirement | Dunst 1.13.2 | Mako 1.11.0 |
|---|---|---|
| FDO Notifications methods | Tagged `src/dbus.c` declares GetCapabilities, Notify, CloseNotification, GetServerInformation. Notify handles replacement ID via shared notification queues. Implements notifications and emits ActionInvoked(id,key) and NotificationClosed(id,reason). | Tagged `dbus/xdg.c` declares/implements the same four standard methods/signals. Notify supports replacement IDs and matching synchronous stack-tag hints; expiry closes and signals. |
| Actions | Accepts incoming action pairs, normal daemon UI can invoke while notification is live. Standard action signal is sent to original D-Bus client; action validity is invalidated on close. Dunst’s docs explicitly say history copies cannot invoke actions. Private NotificationAction is **position-based on currently displayed queue**, not a method “invoke this action key on notification ID.” | Accepts action key/title pairs; external `InvokeAction(us id,key)` finds the exact live notification/action and emits ActionInvoked. Makoctl invoke supports explicit notification ID and action name. Closed/history copies are not in active list for invocation. |

| Change feed / resync | Standard per-client ActionInvoked/NotificationClosed are directed to the notification sender, not a general broadcast stream of every incoming Notify. No explicit event sequence/replay cursor; handle races by connect-monitor-then-fetch/re-fetch. |

The FDO protocol’s CloseNotification reason values are not a universal requirement on callers; both implementations signal reasons, and exact supported meanings should be read from each version’s source rather than inferred from capability names. Dunst emits reason enum mapped to time/user/signal/undefined; Mako defines expired/dismissed/request/unknown in [tagged `include/notification.h`](https://github.com/emersion/mako/blob/v1.11.0/include/notification.h) and sends through `dbus/xdg.c`.

## Integration difficulty and recommendation

**Dunst adapter: Large / high risk** for custom external presentation. Work: (1) make Dunst the exclusive owner of the FDO name and manage activation/start/exit; (2) add or maintain an upstream/private extension for an authoritative active-notification list including original ID, content, actions and image data; (3) provide per-item remaining-time pause/resume if QML hover must suspend expiry; (4) guarantee event ordering, replacement IDs and resync after consumer/daemon restarts; (5) prevent Dunst’s own popups from rendering. Without new API work, event eavesdropping plus `dunstctl history` is incomplete and brittle. Lower difficulty only if qsm accepts Dunst’s own popup and uses QML for history decoration, not replacement UI.

**Mako adapter: Medium-Large / best existing API, but not headless.** Work: (1) exclusive service ownership/Wayland startup; (2) private D-Bus client for `fr.emersion.Mako` snapshot+PropertiesChanged and FDO action/close signals; (3) robust reconnect and snapshot resync; (4) image payload transport gap and timer-state gap; (5) suppress/avoid duplicate Mako renderer. Current private `Notifications` invalidation plus `ListNotifications` makes list synchronization plausible; it still lacks data needed for full-fidelity custom UI and independent hover pause. Styling invisible or alpha-zero is an unsupported rendering hack, not a production backend contract.

**Own implementation: Medium-Large initially, but cleanest for qsm’s requirements and durable control.** Scope is a Qt-side FDO service plus store, ID/replacement semantics, protocol hints/image parsing, per-item timer/pause and close/action semantics; render popup/center directly in QML, maintain an explicit active/historical model and reconnect-free ownership. It prevents sharing two competing renderers and lets qsm define retention/persistence and hover policy. Exact complexity depends on how much FDO compatibility is required: do not treat every optional FDO hint/capability as mandatory; declare truthful capabilities and implement a deliberate interoperable subset. A complete interoperable FDO service is larger than a basic qsm-only service, and should be explicitly scoped.

### Can qsm own popup/lifetime while reusing backend store/timers?

Not fully with either upstream. Mako can provide active data/actions and daemon-owned expiry, but it also owns Wayland surfaces and has no item-level pause or remaining timeout API; a qsm popup would duplicate UI, and hover cannot reliably freeze Mako’s timer. Dunst has pause levels but not a usable active snapshot/exact action API for custom UI, so its timer store is not accessible enough. If external UI is authoritative, either accept a deliberate reduced behavior (daemon decides expiry, qsm does not promise hover pause; disable/hide daemon windows at risk) or own store/timers in qsm. Do not claim backend timers are reused merely because they exist internally.

### Confidence and known unknowns

- **High confidence:** tagged source establishes methods, schema, image parsing, queue/history behavior, startup/build dependencies, and no Mako raw-image list field. These are direct upstream primary sources, not Context7 summaries.
- **High confidence:** Mako does not expose a named headless mode in its v1.11 tagged options/source examined; build requires Wayland. No supported hidden/transparent-only service mode was found. This is absence in inspected tagged upstream docs/build/source, not a claim that a downstream fork cannot patch it.
- **Medium-high confidence:** Dunst history is memory-only and actionless once closed; tagged source/docs confirm lifecycle. Did not exhaust every private extension/version path for any unofficial state API.
- **Unknown:** distro packaging may patch activation/unit files, versions and dependencies; target distribution packaging was not specified. No installed daemon/systemd config or runtime test was performed by instruction.
- **Unknown:** whether qsm product can accept opacity/invisible-window hacks. They are specifically not assessed as production-safe; never call that “headless.”
- **Unknown:** exact user-visible reliability under a live Quickshell/Qt6 compositor; no benchmarks, protocol probes, installed-daemon checks, or lifecycle tests were run.
