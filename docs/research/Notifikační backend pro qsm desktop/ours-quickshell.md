# qsm-desktop notifications: own backend vs Quickshell

## What is implemented, and what is missing?

### Takeaway
The desktop already has a substantial native notification UI, shared QML store, timers, bounded archive, DND/urgency/replacement policy, and a Quickshell D-Bus `NotificationServer` adapter. The adapter is configured honestly not to claim protocol persistence; the largest unresolved items are operational verification of bus activation/round-trip and semantics at the archive/action boundary, not writing a D-Bus daemon from scratch. “Full production-ready” must be scoped: a truthful interoperable server with ephemeral live notifications is materially smaller than durable, actionable history with recovery across shell process restarts.

It explicitly sets `persistenceSupported: false`, `bodyImagesSupported: false`, `bodyHyperlinksSupported: false`, `actionIconsSupported: false`, `inlineReplySupported: false`. - `NotificationStore.qml` owns 5-item popup eligibility, DND (critical bypass), normal/low/critical expiry defaults, replacement for local posts, source syncing, hover pause, close/action callbacks, and history capped at 200 records/16 MiB. History records intentionally contain only archivedAt/appName/summary/body/urgency, not original protocol ID/actions/image. [Local: `NotificationStore.qml:8-26,53-59,121-175,178-235`](file://$HOME/Projects/qsm-desktop/shell/services/NotificationStore.qml)

### Inferences
- Replacing the backend with a third-party daemon is not a UI rewrite: retain `NotificationCenter`, `NotificationStack`, Rollout/DataCapsule, panel and shell-owned surface composition. Replace or adapt only service ownership/record-lifetime/policy boundaries. But any backend that does not supply stable live ID/action semantics, replacement/close signals and DND/expiry hooks requires a compatibility adapter and may alter expected behavior.
- “Own server” already means using Quickshell's C++ D-Bus implementation rather than implementing the protocol. Do not charge the project for reimplementing Notify/GetCapabilities or raw DBus encoding. The desktop's own work is policy, UI, lifecycle, durable model, integration and proof.
- A persisted archive and a persistent protocol notification are different product promises. Existing history is a useful text snapshot; it must not pretend old actions are callable. To offer actionable archived rows across app exit, clients' action endpoints are gone; storing action labels/IDs is insufficient. Define stale-action UX/revalidation (or explicitly make archive inert); a remote action can only be invoked while the originating notification object/client contract remains valid.
- Source shows Quickshell-generation continuity is deliberately available through `keepOnReload`; it is not evidence for supervisor/process crash recovery. Exact lifetime behavior after a shell crash should be treated as unavailable unless client-facing semantics and code establish otherwise. The upstream objects live in the process and there is no disk journal in inspected code.
- Local no-op for archived dismiss is confirmed. Also archive intentionally drops ID/actions; likely desired behavior is archive row removal/clear, not remote dismiss. Resolve API meaning before implementing, rather than reusing live `dismiss(id)`.
- Expected native error/activation races, transport behavior, complete OS-client interoperability and functional capabilities remain unverified. Local status notes active qsm-run/bus owner and prior external tests interrupted; source review is not a passing client round-trip.

### Gaps
- No runtime checking performed by this researcher (assignment prohibited it). Cannot establish current active daemon, successful activation, startup recovery or client round-trip from this lane's read-only source review.
- Source review did not enumerate every FreeDesktop hint's rendering interpretation; upstream preserves `hints`, but whether each supported item is correctly surfaced locally is not proven. Optional capability advertising is truthful for currently disabled feature flags; full spec compliance is a separate question.
- v0.3.0 is the local upstream checkout tag, not confirmation of the installed runtime build's exact version. Deployment/runtime version needs owner verification.

## What does production-ready mean for the current stack?

### Takeaway
For the narrow, honest server scope, finish and verify the existing Quickshell server integration, preserve capability truth, and close obvious record/center semantics. For full persistent/actionable center, add a durable notification model and define recovery/action semantics; this is not a small “turn persistence on” switch. A third-party backend may move protocol ownership, but cannot supply qsm's custom accepted surfaces/policy for free.

### Cited Findings
- Existing system integration requirement says the shell owns `org.freedesktop.Notifications`, swaps out the previous daemon, verifies a real notify/close round-trip, and restores the old daemon on failure within seconds. [Local: `spec/09-input-and-states.md:85-93`](file://$HOME/Projects/qsm-desktop/spec/09-input-and-states.md)
- The local persisted history is expressly bounded JSON; a DB is considered only if searchable/unbounded archive earns it. [Local: `spec/09-input-and-states.md:36-52`](file://$HOME/Projects/qsm-desktop/spec/09-input-and-states.md)
- Notification center requirements include fuzzy search across title/body, grouping by app, default action, Delete/dismiss, DND control, and center-exclusive action route; archive bound 200. [Local: `spec/04-notifications.md:164-180`](file://$HOME/Projects/qsm-desktop/spec/04-notifications.md)
- Quickshell advertises only configured capabilities; action invocation automatically closes a non-resident notification. [Upstream: `server.cpp:142-164`; `notification.cpp:45-56`](https://github.com/quickshell-mirror/quickshell/blob/v0.3.0/src/services/notifications/server.cpp)

### Inferences
- **Minimum production-truthful server (not broad feature parity):** prove activation and ownership on the actual login path, Notify/replacement/Close/action/closed-reason behavior with external clients, failed-claim fallback/rollback, shell reload/crash behavior, and no duplicate daemon/name. Decide/intentionally record supported cap set. Finish center archived-row removal semantics and test long body/image/action/transient/resident/expiry cases. An optional spec feature (inline reply, hyperlinks, images in body, action icons) need not be implemented if not advertised and product does not require it.
- **Full own actionable durable center:** define persistent record schema/versioning; save useful record content and dedupe/replacement lifecycle; durability/atomic writes/limits/search migration; stable local IDs distinct from protocol IDs; hide/reconcile records on remote close, expiry, recall and user dismissal; decide which records archive at all (transient/resident); define action unavailable after source/client disappears, and whether shell must remain up to invoke. Add migration/recovery behavior and UI affordance that does not imply dead actions work. For process restart, cannot resurrect the original remote action object merely from serialized action tuples; policy must say “archived content, no action” or constrain actionable history to live objects within one process. This is a product/architecture boundary, not an implementation detail.
- UI shell-specific experience is largely portable: QML center and popup components are existing reusable types; fullscreen capsule/attached rollout and policy wiring are desktop composition. Swapping daemon source should preserve these if normalized record contract remains stable. Backend state/policy (replacement identity, expiry, action callback and DND admission) is not automatically portable and should stay behind service/store adapter.
- Integration criteria should be explicitly requested and later executed by owner; these notes make no claim of tests passing. Existing 7 Workbench fake/API and 46 production IPC transport tests noted by task prompt are not evidence of D-Bus interoperability and aren't counted as external-backend coverage.

### Gaps
- Full definition of “production-ready” belongs to owner: standard protocol interoperability only, or action-complete archive across crashes too? Those are materially different targets.
- Whether a systemd user service surviving shell UI restart is acceptable would require an architectural product decision and a process-lifetime design; not established by existing local spec. Current Type=exec qsm-run unit supervises shell process, but source alone cannot say what survives its crash.

## Effort comparison (one experienced developer, estimate not measurement)

### Takeaway
The integration-first route is smaller because protocol transport and accepted UI already exist. Estimates assume one full-time developer familiar with Qt/QML/Quickshell, no new design exploration, and include code plus focused verification, not owner acceptance or indefinite cross-desktop support. Ranges are planning judgment from source state, not benchmark or commitment.

### Cited Findings
- Existing protocol/UI/store evidence and gaps are as cited above. The external activation/round-trip and archived dismiss remain pending in local source records. [Local: `spec/04-notifications.md:107-120`; `docs/BACKLOG.md:8-23`](file://$HOME/Projects/qsm-desktop/docs/BACKLOG.md)
- Quickshell upstream's server/protocol implementation and native object lifecycle already exist. [Upstream: `server.cpp:26-58,113-208`; `notification.hpp:61-137`](https://github.com/quickshell-mirror/quickshell/blob/v0.3.0/src/services/notifications/server.cpp)

### Inferences
| Work package | Scope | Optimistic | Typical | Conservative |
|---|---|---:|---:|---:|
| A. Make current native server production-truthful | Read/deploy wiring; D-Bus activation and takeover/restore behavior; verify claimed owner, external Notify/replacement/close/action round-trip and error path; fix defects found; clarify center archived-delete route and regression proof. No broad protocol feature expansion. | 2–3 days | 4–7 days | 8–12 days |
| B. Full durable, actionable-history product | A plus product semantics; durable schema/migration/recovery; source-client loss and stale action behavior; reconciliation and bounds; center remove/clear/search and honest enabled actions; lifecycle/interoperability/failure verification, possibly storage change. | 6–9 days | 12–20 days | 20–35+ days |
| C. External daemon integration, preserve current qsm UI | Remove native name ownership/activation/takeover, configure chosen daemon lifecycle; bridge its notification feed/control API to the existing normalized store/UI if API supports it; preserve DND/expiry/action/close semantics or document changed policy; verify across process restart and display modes. | 3–5 days | 6–10 days | 12–18 days |

- A ranges assume Quickshell API behaves as source suggests. Conservative range allows service activation, ownership race, shutdown/supervisor or distro packaging surprises. “Read/verify” here is a proposed future work item, not performed.
- B range is much wider because “actionable after restart” is not achievable by just storing records: original remote application may no longer have a live action endpoint. If owner accepts inert archived content, reduce B by roughly 3–6 days (schema/persistence/UI semantics still needed); if insists on true remote action after client exit, likely not a well-defined feasible contract without retaining the client-facing service/session and still cannot assume peer survives.
- C depends strongly on the selected daemon. If it provides only standard server ownership (rather than client feed and action bridge), external integration cannot feed the existing center at all without another bridge; the UI can remain but the center may become the daemon's UI or lose archived/history capabilities. If “reuse external” means delegate protocol ownership and discard qsm notifications feature/UI, the project UI removal/work is lower (roughly 2–4 days plus deployment), but that does not preserve current product and is not apples-to-apples.
- A+B are sequentially related; total B includes A integration validation, not add the rows. C does not implement durable archive. External-backend selection alone does not make the current qsm-specific history policy portable.
- Labels: **source-confirmed** = code/spec/backlog evidence above. **Estimate** = judgment only. **Unverified** = runtime owner task. No estimate certifies production quality.

### Gaps
- External-backend lane is intentionally not compared here; no named backend API or scope was supplied to this researcher. Effort C is generic and conditional, not a concrete daemon estimate.
- Actual hidden implementation changes in dirty worktree may alter effort; no implementation/status changes were made or validated here. Notification-related files were locally modified/untracked at inspection; notes rely on current source text, without attribution to who made it.
